# InspireSpec

> **把"设计稿"翻译成"工程规格文档"，让 AI 编码有据可依。**

InspireSpec 是 **InspireDesign 三阶段工具链的第二环**：

```
InspireDesign          InspireSpec            InspireShip（规划中）
灵感 → 设计稿          设计稿 → 工程规格        规格 → 可运行软件
  阶段 0-8               阶段 A-G                阶段 I-V
```

| 阶段 | 工具 | 输入 | 输出 | 目标用户 |
|------|------|------|------|---------|
| 1 | **InspireDesign** | 模糊想法 | UI 设计稿 + 产品文档 | 非设计师 |
| 2 | **InspireSpec** | 设计资产 | 数据模型 + 接口契约 + 状态机 + 测试计划 | 非程序员 / AI 开发者 |
| 3 | InspireShip | 设计 + 规格 | 可编译、可测试、可部署的软件 | AI 编码助手 |

---

## 1. 解决什么问题

InspireDesign 阶段 8（交接开发）完成后，你拥有了完整的 UI 设计资产。但直接进入编码，会遇到：

| 问题 | 表现 | 后果 |
|------|------|------|
| 数据模型未形式化 | 实体字段语义靠注释、靠默契 | 模块间数据不一致 |
| 状态机未定义 | 状态判断散落在 if-else 中 | 修一个 Bug 引入另一个 |
| 接口契约缺失 | 模块间输入输出没有约定 | 集成时接口不匹配 |
| 需求追踪缺失 | 不知道哪些设计点已实现、哪些遗漏 | 功能遗漏，审查才发现 |
| 测试策略缺失 | 没有测试计划和用例 | 回归无验证 |

**InspireSpec 把这些"应该在编码之前想清楚的事"，变成有模板、有检查清单、有质量门禁的结构化流程。**

## 2. 核心主张

> **代码可以重写，但工程纪律不能跳过。**
>
> AI 写代码越快，你越需要工程纪律来保证方向正确。
> 没有指南针的快艇，比没有指南针的独木舟更危险。

### 2.1 与 InspireDesign 相同的设计哲学

| 原则 | InspireDesign | InspireSpec |
|------|--------------|-------------|
| 文本为事实来源 | HTML+CSS 是设计源 | Markdown 是规格源 |
| 声明式环境要求 | 工具声明环境清单，AI 执行检查 | 模板声明字段约束，AI 执行填充 |
| 人做决策 | 人确认"这个设计行不行" | 人确认"这份规格对不对" |
| 粗粒度、无状态 | 一个 `get_stage_guidance` 返回完整约束包 | 一个 `get_stage_checklist` 返回完整检查清单 |
| 可回退 | 改了 tokens 告知下游影响面 | 改了数据模型告知哪些接口/测试需复查 |

### 2.2 AI 协作模式的特别适配

传统软件工程流程假设团队里有 PM、架构师、QA。InspireSpec 针对 **"一人 + AI"模式**做了适配：

| 传统角色 | InspireSpec 中的执行方式 |
|---------|------------------------|
| 架构师定义数据模型 | AI 从设计文档提取实体草稿 → 人审批 |
| QA 写测试计划 | AI 从状态机生成测试用例框架 → 人确认覆盖度 |
| 开发写接口文档 | AI 从代码提取 public 方法签名 → 人补充语义说明 |
| PM 维护需求追踪 | AI 从设计文档提取需求点 → 人确认优先级 |

**关键：AI 做"提取和结构化"，人做"审批和决策"。**

## 3. 流程全景（A-G 阶段）

| 阶段 | 名称 | 核心产物 | 质量门禁 |
|------|------|---------|---------|
| **A** | 设计接收、PRD 与差距分析 | 设计资产清单 + PRD + 差距报告 | 需求范围、验收标准和差距项已确认 |
| **B** | 数据建模、实体定义与通用约束 | 数据字典 + ER 图 + 通用约束 | 每个实体字段有定义；P0/P1 规则有测试点 |
| **C** | 接口契约、状态机与核心时序 | 模块接口文档 + 状态转换图 + sequenceDiagram | 每个模块输入输出有契约；核心流程无歧义 |
| **D** | 4+1 视图、实现规划与任务分解 | 架构 4+1 视图 + 需求追踪矩阵 + 任务清单 | 关键场景能被架构视图解释；依赖无环 |
| **E** | 编码实现与单元测试 | 代码 + 单元测试 + 变更日志 | 核心逻辑有测试；每次提交通过全部测试 |
| **F** | 集成测试与回归验证 | 测试报告 + 缺陷清单 | 设计-实现逐项对照通过；无 P0/P1 缺陷 |
| **G** | 发布准备与复盘 | 发布清单 + 复盘报告 | 部署验证通过；复盘改进项已记录 |

每个阶段的约束包由这些字段组成：

**目标 / 产物 / 出口条件 / 规则 / 模板 / 提示词模板 / 依赖 / 常见坑 / 回退影响面 / 检查清单。**

## 6. 与 InspireDesign 的衔接

### 交接物

InspireDesign 阶段 8 完成后，以下资产移交给 InspireSpec 阶段 A：

| 资产 | 格式 | 消费阶段 |
|------|------|---------|
| 功能蓝图 | Markdown | A（形成 PRD）/ D（建立 RTM） |
| 页面流转图 | Mermaid HTML | C-D（形成时序图与实现顺序） |
| 设计令牌 | CSS | E（编码引用） |
| 组件库（全状态） | CSS | F（视觉对照） |
| 主界面 + 规格页 | HTML | F（设计一致性审查） |
| 技术映射表 | Markdown | E（编码参照） |
| 历次裁定记录 | Markdown | A-B（确认 PRD 与通用约束） |
| 硬件/部署初始条件 | Markdown/表格 | D-G（形成物理视图、部署清单、验收计划） |

### 回退协议

如果 InspireSpec 阶段发现问题需要回退到 InspireDesign：

| 触发条件 | 回退到 | 影响面 |
|---------|--------|--------|
| UI 交互规格不足 | 阶段 5（画规格页） | 补充后重新走 A |
| 组件状态定义不全 | 阶段 3（搭组件库） | 补充后重新走 A-B |
| 功能范围需要调整 | 阶段 0（功能蓝图） | 全链路重新走 |
| 技术映射发现不可行 | 阶段 7（写映射） | 修改后重新走 A |

## 7. 演进路线

| 阶段 | 形态 | 状态 |
|------|------|------|
| 方法论 + 模板 + 提示词 | Markdown 文档集 | **当前** |
| 数据外置化 | `data/stages.js` 机器可读约束包（结构见 [10-数据契约.md](./docs/10-数据契约.md)） | 规划中 |
| MCP 服务 | `get_stage_checklist(stage)` 等工具（设计见 [10-数据契约.md](./docs/10-数据契约.md) §4） | 规划中 |
| 自动化检查 | 数据字典一致性检查、状态机完整性检查 | 规划中 |

演进原则：**先固化、边用边改、不过度设计。** 先在真实项目中走完全流程，积累经验后再抽象为工具。

## 8. 这不是什么

| 不是 | 说明 |
|------|------|
| 不是代码生成器 | 不直接生成业务代码（那是 InspireShip 的事） |
| 不是项目管理工具 | 不做排期/工时/看板 |
| 不是测试执行器 | 只定义测试策略和用例框架，不执行测试 |
| 不是 InspireDesign 的替代品 | 是下游衔接，不是竞争关系 |

## 9. 命名说明

为什么叫 InspireSpec 而不是其他名字？详见 [项目命名说明.md](./项目命名说明.md)。

核心原因：三阶段工具链 Design → Spec → Ship，每个名字描述该阶段的核心产物。Spec = Specification = 工程规约，短、好记、开发者直觉理解。
