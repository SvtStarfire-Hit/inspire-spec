# 11-双轨制与验收驱动

> **核心转变：从"流程引导 AI 走步骤"到"定义约束壳让 AI 朝验收点努力"。**
>
> 每个阶段的产出分为两套文档：A 系列给人看（工程文档），B 系列给 AI 用（验收驱动的约束壳）。人看得明白，AI 写有目的——而不是写成伪代码让 AI 做翻译。

---

## 1. 核心原则

### 1.1 问题：散文式方案为什么对 AI 无效

AI 处理"散文式方案"效果下降的根本原因：

| 信息形态 | 人类处理方式 | AI 处理方式 | 对 AI 的效果 |
|----------|-------------|------------|-------------|
| 叙述性散文 | 脑补意图、抓重点 | 把每句话当潜在指令 | 选择空间爆炸，结果不可控 |
| 伪代码/步骤 | 理解思路，细节临场判断 | 忠实执行但遇歧义就乱猜 | 在模糊地带"创造性发挥" |
| 结构化约束 | 感觉受限 | 搜索空间缩小，结果收敛 | **最优** |

**结论：给 AI 的工程文档，应该是"约束壳"而不是"实现剧本"。**

### 1.2 双轨制：同源两套产出

每个阶段的分析产出**同一份理解**，但分两套文档服务不同消费者：

```
阶段分析（做什么 + 不能怎么做 + 怎么算对）
        │
        ├── A 系列（An）── 给人看 ── 健壮工程文档，团队交流/项目把控/评审归档
        │
        └── B 系列（Bn）── 给 AI 用 ── 验收驱动，约束壳，可执行验收点
```

### 1.3 B 系列三要素

每个 B 系列文档必须包含三个核心部分：

| 要素 | 回答的问题 | 对 AI 的作用 |
|------|-----------|-------------|
| **边界约束** | "什么不能碰、什么不能用、什么模式必须遵守" | 缩小搜索空间，防止 AI 乱发挥 |
| **接口签名** | "对接点长什么样" | 消除猜测成本，确定性信息 |
| **验收用例** | "怎么算做对了" | 提供客观反馈信号，AI 朝此努力 |

> **边界约束是最重要的详细。** 约束写得越死，AI 乱发挥的空间越小。对人类来说是"限制"，对 AI 来说是"导航"。

### 1.4 与传统伪代码/流程图的区别

| 维度 | 传统伪代码/流程图（给人类） | B 系列规格（给 AI） |
|------|---------------------------|-------------------|
| 核心内容 | "怎么做"（步骤 1→2→3） | "做成什么样 + 不能怎么做" |
| 信息形态 | 叙述性（故事/流程） | 约束性（边界 + 接口 + 验收） |
| AI 的角色 | 执行者（按步骤走） | 求解者（在约束壳内找最优解） |
| 质量保障 | 人工 review 代码 | 跑验收用例，过则通过 |

## 2. 各阶段双轨产出

| 阶段 | A 系列（人读 · 工程文档） | B 系列（AI 用 · 约束壳） |
|------|-------------------------|-------------------------|
| **A** 需求接收 | PRD：业务目标、范围、用户故事、验收标准 | **需求验收表**：每条需求 → 可测试的行为断言 + 边界条件 + 排除项 |
| **B** 数据建模 | 数据字典 + ER 图 + 通用约束文档 | **数据契约规格**：每个字段 → 类型/约束/默认值 + 验证规则 + 关联影响面 |
| **C** 接口契约 | 接口文档 + 状态机图 + 时序图 | **接口规格 + 状态规格**：签名/幂等/权限 + 状态转换的 输入→输出→异常 用例 |
| **D** 架构 | 4+1 视图 + 需求追踪矩阵 | **模块边界规格**：模块职责/禁止越界 + 依赖约束 + 场景→模块追踪断言 |
| **E** 编码 | 变更日志 + 代码注释 | **编码任务卡**：接口签名 + 禁止事项 + 必须通过的测试用例 |
| **F** 测试 | 测试计划 + 测试报告 | **可执行验收集**：测试用例 + 期望输入输出 + 通过/失败判定标准 |
| **G** 发布 | 发布清单 + 复盘报告 | **部署验收规格**：环境约束 + 冒烟测试 + 回滚条件 |

**A 系列是传统工程文档**——团队评审、归档、交流的标准产物。

**B 系列是验收驱动的结构化规格**——AI 直接消费，不需要再"翻译"。B 系列本身就是最好的提示词，不需要额外的 `aiPromptTemplate`。

## 3. 工程图示在双轨制中的位置

### 3.1 工程图示在哪个阶段产出

工程图示在双轨制中**主要属于 A 系列**——它是给人看的可视化沟通工具。但每种图示的形式化语义可以**衍生出 B 系列的验收规格**。

下表说明每种图示在哪个阶段产出、所属记法体系、如何衍生：

| 阶段 | 图示 | 记法来源 | A 系列（人读 · 沟通工具） | 衍生 B 系列（AI 用 · 验收规格） |
|------|------|----------|-------------------------|-------------------------------|
| **B** 数据建模 | ER 图 | ER 记法（Peter Chen, 1976） | 实体关系的可视化展示 | → 数据验证规则（字段类型/约束/外键/唯一性断言） |
| **C** 接口契约 | 状态机图 | UML State Machine Diagram | 状态流转的可视化说明 | → 状态转换测试用例（合法转换 + 非法转换 + 边界状态） |
| **C** 接口契约 | 时序图 | UML Sequence Diagram | 模块调用顺序的可视化 | → 接口调用序列断言（正常路径 + 异常路径 + 超时场景） |
| **C** 接口契约 | 类图 | UML Class Diagram | 类型结构的可视化 | → 接口签名（方法名/参数/返回类型/可见性） |
| **D** 架构 | 4+1 视图 | Kruchten 4+1 框架（1995） | 系统架构的多视角可视化 | → 模块边界约束（依赖方向/禁止跨层调用/部署映射断言） |

> **工程图示集中在 B-D 阶段产出**：B 阶段产 ER 图，C 阶段产状态机图/时序图/类图，D 阶段产 4+1 视图。A 阶段不涉及图示（需求层面还没到可视化），E-G 阶段不产新图（消费前序阶段的图）。

### 3.2 关键原则

**工程图示不能只停留在“图”的层面。** 产出图示时必须同步提取其形式化语义，作为 B 系列的验收规格输入。

> 例：画完状态机图后，不能只交一张图——必须同时产出"从 idle 状态收到 start 信号 → 必须转为 running；从 running 收到 start 信号 → 必须拒绝并返回 ALREADY_RUNNING"这样的结构化断言。

## 4. 改造方案

### 4.1 约束包字段调整

当前 StageContract 的 14 字段需要调整重心，从"流程引导"转向"验收驱动"：

| 字段 | 处置 | 理由 |
|------|------|------|
| `id` | **保留** | 通用 |
| `number` | **保留** | 通用 |
| `name` | **保留** | 通用 |
| `goal` | **保留** | 通用 |
| `deliverables` | **拆分** → `aDeliverables` + `bDeliverables` | A 系列产物 vs B 系列产物 |
| `exitCriteria` | **保留并强化** → 必须包含 B 系列验收通过条件 | 出口条件不能只检查"文档写了"，还要检查"验收点可执行" |
| `dependencies` | **保留** | 通用 |
| `rules` | **保留并强化** → 作为边界约束的基础 | 规则是 B 系列边界约束的来源 |
| `guidance` | **弱化** → 改为 `aGuidance`（给人看的流程建议） | 不再作为 AI 的执行指令 |
| `aiPromptTemplate` | **废弃** → B 系列文档本身就是最好的提示词 | 不再需要额外的"伪代码式"提示词 |
| `pitfalls` | **保留** | 通用 |
| `revisionImpact` | **保留** | 通用 |
| `humanCheckpoint` | **保留** | 通用 |
| `checklist` | **保留** | 通用 |

新增字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `boundaryConstraints` | string[] | 边界约束：禁止改什么、禁止用什么、必须遵守什么模式 |
| `acceptanceCriteria` | object[] | 验收用例：`{ scenario, given, when, then }` 格式 |
| `interfaceSignatures` | object[] | 接口签名：`{ name, params, returns, description }`（适用于 C-E 阶段） |

### 4.2 改造步骤

| 步骤 | 内容 | 影响文件 |
|------|------|---------|
| **①** | **确立双轨核心思想**：在核心方法论中引入"约束壳 vs 实现剧本"的区别，明确 B 系列三要素（边界/接口/验收） | `01-核心方法论.md` |
| **②** | **改造数据契约**：StageContract 新增 `boundaryConstraints`、`acceptanceCriteria`、`interfaceSignatures`；`deliverables` 拆为 A/B 两系列；废弃 `aiPromptTemplate` | `data/stages.js`、`docs/10-数据契约.md` |
| **③** | **改造各阶段内容**：每个阶段补充边界约束和验收用例；`guidance` 改为 A 系列流程建议；`aiPromptTemplate` 替换为 B 系列文档的结构化描述 | `data/stages.js`、`docs/03-阶段流程与质量门禁.md` |
| **④** | **调整 MCP 工具**：新增 `get_acceptance_spec(scene, stage)` 返回 B 系列规格（边界+接口+验收）；`get_stage_checklist` 保留用于 A 系列流程引导 | `mcp-server.js`、`test-mcp.js` |
| **⑤** | **更新页面端**：B 系列视图（约束壳浏览：边界/接口/验收三个板块）；A/B 切换标签 | `web/assets/app.js`、`web/assets/app.css` |
| **⑥** | **更新文档导航和 README** | `00-目录导航.md`、`README.md` |

### 4.3 改造后的约束包结构（预览）

```
StageContract（改造后）
├── 通用字段
│   ├── id / number / name / goal
│   ├── dependencies / pitfalls / revisionImpact
│   ├── humanCheckpoint / checklist
│   └── exitCriteria（强化：含 B 系列验收通过条件）
│
├── A 系列字段（给人看）
│   ├── aDeliverables        ← 原 deliverables 中偏文档的产物
│   ├── aGuidance            ← 原 guidance，改为流程建议
│   └── rules                ← 保留，作为边界约束的基础
│
├── B 系列字段（给 AI 用）
│   ├── bDeliverables        ← 原 deliverables 中偏规格的产物
│   ├── boundaryConstraints  ← 新增：禁止/必须约束
│   ├── interfaceSignatures  ← 新增：接口签名（C-E 阶段）
│   └── acceptanceCriteria   ← 新增：可测试的验收用例
│
└── 废弃字段
    └── aiPromptTemplate     ← B 系列文档本身就是提示词
```

### 4.4 改造原则

1. **渐进式改造**：先改数据契约和 1-2 个阶段（如 C、E）做样板，验证可行后再推广到全部阶段
2. **A/B 不互斥**：同一阶段分析同时产出两套文档，不是二选一
3. **B 系列可执行**：验收用例应该是"可运行的测试用例"或"可验证的断言"，不是描述性文字
4. **图示必须衍生**：每种工程图示必须同步产出对应的 B 系列验收规格，不能只交图

## 5. 与 InspireDesign 的关系

InspireDesign 已经实现了"同一份内容，两个消费形态"（页面端给人、MCP 给 AI）。InspireSpec 的双轨制是这个思想的**深化**：

| 维度 | InspireDesign | InspireSpec（改造后） |
|------|--------------|---------------------|
| 同源双消费 | 页面端（教程版）+ MCP（指令版） | A 系列（工程文档）+ B 系列（约束壳） |
| 给 AI 的形态 | 约束包（guidance + promptTemplate） | B 系列（边界 + 接口 + 验收） |
| 本质区别 | 同一内容的两种表述 | **两种完全不同的信息结构**，服务不同目的 |

InspireDesign 的双消费是"同内容不同措辞"；InspireSpec 的双轨制是"同分析不同结构"——A 系列是给人理解的叙述，B 系列是给 AI 执行的约束。
