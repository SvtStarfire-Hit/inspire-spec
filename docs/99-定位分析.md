# InspireSpec 定位分析：从软件工程视角看它是什么

> "方法论"是对外传播时的说法。本文从软件工程学科角度，分析 InspireSpec 在不同视角下的准确定位。

---

## 1. 核心问题

InspireSpec 解决的是"设计想法"到"编码实现"之间的断层。

用软件工程的话说，它补上的是被跳过的**需求工程环节**。

---

## 2. 不同视角下的准确描述

### 2.1 需求工程（Requirements Engineering）

软件工程学科中最对应的正式分支。包含三个核心活动：

| 活动 | 含义 | 对应 InspireSpec |
|------|------|-----------------|
| Requirements Elicitation | 从设计稿、利益相关者中提取真实需求 | 阶段 A：设计接收与差距分析 |
| Requirements Specification | 将需求写成形式化文档 | 阶段 B-C：PRD、数据字典、通用约束、接口契约 |
| Requirements Validation | 验证需求是否完整、一致、可测试 | 阶段 D：RTM、4+1 视图 |

**判断**：InspireSpec 本质上是一个需求工程工具链。

---

### 2.2 软件规约（Software Specification）

"规约"比"规格"更精确。在软件工程中：

- **Specification** = 对系统行为的精确、可验证的描述
- 它不是"大概怎么做"，而是"必须满足什么约束"

InspireSpec 的产物——数据字典、接口契约、通用约束、状态机、时序图——都是不同维度的规约。

中文里三个词容易混淆：

| 词 | 含义 | 对应 |
|---|------|------|
| 规格 | 详细描述"是什么" | Specification |
| 规约 | 约定必须遵守的约束 | Convention / Contract |
| 规范 | 推荐遵循的标准 | Standard / Guideline |

**判断**：InspireSpec 同时涵盖这三层——数据字典是规格，接口契约是规约，最佳实践是规范。

---

### 2.3 前端加载工程（Front-End Loading, FEL）

来自系统工程和工业工程，核心主张：

> 在动手之前，把决策成本前置。项目早期投入越多的工程定义工作，后期变更成本越低。

InspireSpec 的 A-G 阶段就是一个典型的 FEL 流程——在编码之前，把 PRD、数据模型、接口契约、架构视图全部定义清楚。

**判断**：InspireSpec 是一种前端加载工程实践。

---

### 2.4 设计规约化（Design Specification）

IEEE 标准体系中有明确区分：

```
SRS  → Software Requirements Specification   （软件需求规约）
SDD  → Software Design Description            （软件设计描述）
```

InspireSpec 横跨这两者：

| IEEE 产物 | 内容 | 对应 InspireSpec 阶段 |
|-----------|------|----------------------|
| SRS | 功能需求、非功能需求、数据定义、约束 | 阶段 A-B：PRD、数据字典、通用约束 |
| SDD | 架构视图、接口设计、行为描述 | 阶段 C-D：接口契约、时序图、4+1 视图 |

**判断**：InspireSpec 是一个设计规约化过程。

---

### 2.5 V 模型左侧（V-Model Left Side）

软件工程经典的 V 模型：

```
        需求分析 ─────────────── 验收测试
         │                        ↑
       概要设计 ──────────────── 集成测试
         │                        ↑
       详细设计 ──────────────── 单元测试
         │                        │
         └──────→ 编码 →──────────┘
```

V 模型左侧 = "定义做什么、怎么做"，右侧 = "验证做对没有"。

InspireSpec 覆盖的是 **V 模型左侧的完整工程化过程**，同时通过 RTM 和测试计划模板把左右两侧连起来。

**判断**：InspireSpec 是 V 模型左侧的实操落地。

---

### 2.6 阶段门控流程（Stage-Gate Process）

从项目管理角度看，InspireSpec 的 A-G 阶段 + 质量门禁就是一个 Stage-Gate 流程：

```
Stage A → Gate → Stage B → Gate → Stage C → ... → Stage G
```

每个 Gate 有明确的出口条件：

| 阶段 | 出口条件 |
|------|----------|
| A → B | 需求范围和验收标准已确认 |
| B → C | 字段语义唯一，P0/P1 规则有测试点 |
| C → D | 核心流程和异常路径无歧义 |
| D → E | 需求可追踪，依赖无环 |

不满足条件，不进入下一阶段。

**判断**：InspireSpec 是一个阶段门控流程。

---

## 3. 总结

| 视角 | 最准确的描述 | 一句话 |
|------|-------------|--------|
| 软件工程学科 | **需求工程** | 从利益相关者意图到可验证规格的全过程 |
| 产出物角度 | **软件规约** | 对系统行为的多维度精确描述 |
| 系统工程角度 | **前端加载工程** | 把决策成本前置到动手之前 |
| IEEE 标准角度 | **设计规约化** | SRS + SDD 的形式化过程 |
| 质量模型角度 | **V 模型左侧** | 定义"做什么"并建立验证依据 |
| 项目管理角度 | **阶段门控流程** | 每阶段有入口、产物和出口条件 |
| 对外传播角度 | **方法论** | 当前 InspireSpec 使用的说法 |

如果只能选一个最准确的软件工程术语：**需求工程**。

因为 InspireSpec 的核心价值就是——在"设计想法"和"编码实现"之间，补上被跳过的需求工程环节。
