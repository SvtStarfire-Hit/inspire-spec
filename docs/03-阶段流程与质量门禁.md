# 03-阶段流程与质量门禁

> 本文档把 InspireSpec 拆成 A-G 七个阶段。每个阶段都有完整的约束包定义。
>
> 每个阶段的通用交互约定：
>
> - 开始前：AI 检查"依赖"中的前置产物是否已存在；缺则先回补
> - 结束时：AI 停下来，把产出摆给人看，等人说"行"或提修改
> - 回退时：按"回退影响面"提示需要复查的下游文件

---

## 1. 阶段总览

| 阶段 | 名称 | 输入 | 产物 | 出口条件 |
|------|------|------|------|----------|
| A | 设计接收、PRD 与差距分析 | 功能设计、界面设计、交互说明 | 设计资产清单、PRD、差距报告 | 需求范围和验收标准已确认 |
| B | 数据建模与通用约束 | PRD、设计稿、已有代码/数据库 | 数据字典、ER 图、通用约束 | 字段语义唯一，P0/P1 规则有测试点 |
| C | 接口契约、状态机与核心时序 | 数据字典、通用约束、模块草图 | 接口/API/设备契约、状态图、时序图 | 核心流程和异常路径无歧义 |
| D | 4+1 视图与实现规划 | PRD、契约、时序图 | 4+1 视图、RTM、任务清单 | 需求可追踪，依赖无环 |
| E | 编码实现与单元测试 | 任务清单、规格文档 | 代码、单元测试、变更日志 | 核心逻辑有测试，变更影响面已记录 |
| F | 集成测试与回归验证 | 代码、测试计划、RTM | 测试报告、缺陷清单 | 无 P0/P1 缺陷，设计实现一致 |
| G | 发布准备与复盘 | 测试结论、部署清单 | 发布清单、复盘报告 | 部署验证通过，经验已沉淀 |

## 2. 阶段 A：设计接收、PRD 与差距分析

| 字段 | 内容 |
|------|------|
| 目标 | 确认上游设计资产能否进入工程实现，并把分散的功能说明整理成 PRD |
| 产物 | （1）设计资产清单（2）PRD 产品需求文档（范围/角色/功能/验收标准/非功能需求）（3）差距报告（工程维度差距与处置建议） |
| 出口条件 | 每个核心功能都有验收标准；范围外已明确；差距项有严重度和处置阶段 |
| 依赖 | InspireDesign 阶段 8 的交接资产（功能蓝图、页面流转图、设计令牌、组件库、界面稿、技术映射表） |
| 规则 | 先清点再分析；验收标准必须可验证（"用户能…"不算，"系统在 X 条件下 Y 秒内返回 Z"才算）；不在此阶段做数据建模或架构决策；差距报告必须按工程维度分类（数据/约束/接口/状态/架构/测试/部署） |
| AI 引导要点 | 1. 逐项清点设计资产，确认哪些齐全、哪些缺失 2. 从功能蓝图提取用户角色和业务场景 3. 引导为每个核心功能写验收标准 4. 识别工程差距并分类 5. 标出需要人工裁定的问题（范围边界、优先级冲突） |
| 提示词模板 | 见 [06-AI协作提示词.md](./06-AI协作提示词.md) §1 |
| 常见坑 | 跳过差距分析直接编码（后续必然返工）；验收标准写成"功能正常"（不可验证）；把范围外的需求混进 PRD；让 AI 自行裁定业务冲突 |
| 回退影响面 | 改范围 → 下游所有阶段受影响（尽早确认）；改验收标准 → 测试计划需同步 |
| 人确认点 | 范围/范围外认同？验收标准可验证？差距项处置方案合理？ |

### 门禁清单

- [ ] 每个核心功能都有可验证的验收标准。
- [ ] 范围外已明确列出。
- [ ] 差距项有严重度（P0/P1/P2）和处置阶段。
- [ ] 需要人工裁定的问题已标出，未被 AI 自行决定。

## 3. 阶段 B：数据建模与通用约束

| 字段 | 内容 |
|------|------|
| 目标 | 统一实体、字段、枚举、关系和跨模块业务规则 |
| 产物 | （1）数据字典（实体/字段/类型/约束/默认值/语义）（2）ER 图（Mermaid `erDiagram`）（3）通用约束与业务规则（编号/等级/影响模块/测试点） |
| 出口条件 | 每个共享字段语义唯一；每个状态字段有进入条件和可转换目标；P0/P1 规则有编号和测试点 |
| 依赖 | 阶段 A 的 PRD；设计稿中的数据相关界面；已有代码/数据库（如有） |
| 规则 | 布尔字段必须写清 true/false 的精确定义；状态字段优先使用枚举而非布尔；共享字段变更必须同步接口契约和测试；通用约束必须集中编号，不散落在各模块文档中；P0/P1 规则必须能转化为可执行的测试用例 |
| AI 引导要点 | 1. 从 PRD 和设计稿提取所有核心实体 2. 为每个字段定义类型、约束、默认值、语义 3. 找出语义模糊或多模块共用的字段，提请人裁定 4. 绘制 ER 图 5. 提取通用约束并编号 6. 对比现有代码/数据库列出偏差 |
| 提示词模板 | 见 [06-AI协作提示词.md](./06-AI协作提示词.md) §2 |
| 常见坑 | 字段语义靠猜（同一字段在不同模块含义不同）；布尔字段不写精确定义；通用约束散落在代码注释和口头说明中；状态字段用布尔而非枚举（后续必然扩展爆炸）；只建模正常数据，忽略空值/默认值/边界值 |
| 回退影响面 | 改实体结构 → 接口契约需同步；改字段语义 → 所有引用该字段的模块需复查；改通用约束 → 相关测试用例需更新 |
| 人确认点 | 字段语义是否唯一？枚举值是否完备？P0/P1 规则是否覆盖核心业务？ |

### 门禁清单

- [ ] 每个共享字段语义唯一，无歧义。
- [ ] 每个状态字段有进入条件和可转换目标。
- [ ] P0/P1 规则有编号和对应的测试点。
- [ ] 与现有代码/数据库的偏差已记录。

## 4. 阶段 C：接口契约、状态机与核心时序

| 字段 | 内容 |
|------|------|
| 目标 | 定义模块、前后端、设备之间如何交互，并明确关键流程顺序 |
| 产物 | （1）接口/API/设备契约（输入/输出/副作用/异常/权限/幂等性）（2）核心流程时序图（Mermaid `sequenceDiagram`，含正常和异常路径）（3）状态机图（Mermaid `stateDiagram-v2`，用于复杂状态对象） |
| 出口条件 | 每个跨模块调用有契约；每个核心流程有时序图；异常路径有处理策略 |
| 依赖 | 阶段 B 的数据字典和通用约束；模块/API/设备列表 |
| 规则 | 每张时序图至少包含一个异常分支（`alt/else`）；图中的模块名必须与接口契约中的名称一致（禁止同一模块在不同文档中使用不同名字）；接口契约必须覆盖副作用和幂等性；设备通信契约必须包含超时/重试/心跳 |
| AI 引导要点 | 1. 列出所有跨模块调用点（API/事件/设备/文件） 2. 为每个接口写输入/输出/副作用/异常/权限 3. 为主业务链路画时序图 4. 为异常链路补充 `alt/else` 分支 5. 为复杂状态对象画状态图 6. 检查接口调用两端是否匹配 |
| 提示词模板 | 见 [06-AI协作提示词.md](./06-AI协作提示词.md) §3 |
| 常见坑 | 只有模块没有流程（代码模块都有但串不起来）；时序图只画正常路径（异常上线后爆雷）；接口两端参数不匹配（调用方和被调方定义不一致）；设备通信不写超时和重试策略；Mermaid 图中的模块名与接口契约中的名字不一致 |
| 回退影响面 | 改接口签名 → 调用方和被调方都需复查；改状态机 → 相关时序图和测试用例需同步；改异常策略 → 时序图和通用约束需同步 |
| 人确认点 | 接口契约的输入输出是否完整？异常路径的处理策略是否合理？状态转换是否覆盖所有场景？ |

### 门禁清单

- [ ] 每个跨模块调用有契约（含输入/输出/异常）。
- [ ] 每个核心流程有时序图，且包含至少一个异常分支。
- [ ] 复杂状态对象有状态机图。
- [ ] 接口调用两端参数匹配。

## 5. 阶段 D：4+1 视图与实现规划

| 字段 | 内容 |
|------|------|
| 目标 | 从架构角度确认系统边界，建立需求追踪，并拆解实现任务 |
| 产物 | （1）架构 4+1 视图（用例/逻辑/开发/进程/物理）（2）需求追踪矩阵 RTM（需求→设计→接口/模块→代码→测试）（3）任务清单（含依赖关系和实现顺序） |
| 出口条件 | 每个需求有实现和测试落点；每个核心场景能被架构视图解释；任务依赖无环 |
| 依赖 | 阶段 A 的 PRD；阶段 C 的契约和时序图；技术栈/部署/硬件条件 |
| 规则 | 进程视图不能只画分层，必须包含线程/队列/并发/失败隔离；物理视图不能只画服务器，必须包含设备/网络/端口/驱动/模型；RTM 中每条需求至少关联设计来源、实现模块、测试用例；任务拆解必须标注依赖，且依赖无环 |
| AI 引导要点 | 1. 从 PRD 提取用例和角色 2. 从契约提取模块和领域对象 3. 生成 5 个视图的草稿 4. 建立 RTM 映射 5. 拆解任务并标注依赖 6. 检查孤儿需求和幽灵实现 |
| 提示词模板 | 见 [06-AI协作提示词.md](./06-AI协作提示词.md) §4-5 |
| 常见坑 | 架构只画分层不画运行和部署（并发/性能/部署问题后置暴露）；RTM 只建不维护（沦为摆设）；任务拆太粗（无法估算和追踪）；依赖有环（无法确定实现顺序）；软硬件项目不画物理视图（到现场才发现依赖缺失） |
| 回退影响面 | 改架构视图 → 任务清单和 RTM 需同步；改任务依赖 → 实现顺序需重排；发现新需求 → 回 PRD 补后重走 RTM |
| 人确认点 | 5 个视图是否覆盖核心场景？RTM 无孤儿/幽灵？任务拆解粒度和顺序合理？ |

### 门禁清单

- [ ] 每个需求有实现和测试落点（RTM 无空白行）。
- [ ] 每个核心场景能被架构视图解释。
- [ ] 任务依赖无环。
- [ ] 无孤儿需求（有需求无实现）和幽灵实现（有实现无需求）。

## 6. 阶段 E：编码实现与单元测试

| 字段 | 内容 |
|------|------|
| 目标 | 在规格约束下完成编码实现，并同步产出单元测试和变更日志 |
| 产物 | （1）可编译/可运行的代码（2）单元测试（覆盖核心逻辑和 P0/P1 规则）（3）变更日志（每次关键改动的原因和影响面） |
| 出口条件 | 核心逻辑有单元测试；所有测试通过；每次关键改动都记录了变更日志；修改字段/规则/接口时文档已同步更新 |
| 依赖 | 阶段 D 的任务清单；阶段 B 的数据字典；阶段 C 的接口契约和时序图；阶段 B 的通用约束 |
| 规则 | 先读规格，再写测试，再写代码（TDD 精神：规格驱动实现）；修改规则、字段、接口时必须同步更新对应文档（不允许"代码改了文档以后补"）；每次关键改动写变更日志（原因/影响面/关联需求编号）；不允许一次性实现所有任务——按任务清单顺序逐个实现、逐个验证 |
| AI 引导要点 | 1. 按任务清单顺序取下一个任务 2. 读取相关的规格文档（数据字典/接口契约/约束） 3. 先写测试（或至少同时写） 4. 再写实现 5. 跑测试确认通过 6. 记录变更日志 |
| 提示词模板 | 编码时引用阶段 D 的任务编号，格式："请实现任务 [编号]，参考以下规格文档：[路径列表]" |
| 常见坑 | 不读规格直接编码（实现偏离规格）；改了字段/接口不同步文档（文档与代码分裂）；不写单元测试（后续回归无验证）；一次性铺开所有任务（无法追踪进度和问题）；变更日志写空泛的"修复 Bug"（应写清根因和影响面） |
| 回退影响面 | 发现规格有误 → 回对应阶段（A-D）修正 → 已实现的相关代码需复查；发现测试策略不足 → 回阶段 D 补测试计划 |
| 人确认点 | 每个任务完成后确认实现是否符合规格；关键架构决策是否按规格执行？ |

### 门禁清单

- [ ] 核心逻辑有单元测试，且全部通过。
- [ ] 修改字段/规则/接口时文档已同步。
- [ ] 每次关键改动有变更日志记录。
- [ ] 无跳过规格直接实现的情况。

## 7. 阶段 F：集成测试与回归验证

| 字段 | 内容 |
|------|------|
| 目标 | 证明实现符合设计：逐条验证需求、验证核心链路、验证异常路径 |
| 产物 | （1）测试报告（按 RTM 逐项对照结果）（2）缺陷清单（含严重度分级和根因分类） |
| 出口条件 | RTM 逐项验证通过；无 P0/P1 缺陷；设计文档与实现一致（无偏移）；异常路径和边界条件已验证 |
| 依赖 | 阶段 E 的代码和单元测试；阶段 D 的 RTM 和测试计划；阶段 C 的时序图（异常路径）；阶段 B 的通用约束（P0/P1 规则） |
| 规则 | 按 RTM 逐项验证（不允许只挑"好测的"测）；按通用约束验证 P0/P1 规则（从约束文档直接生成测试点）；按时序图验证主链路和异常链路（不能只测正常路径）；缺陷必须分类根因（需求不清/数据不清/约束缺失/接口不清/流程不清/测试缺失）——这个分类直接喂给阶段 G 的复盘 |
| AI 引导要点 | 1. 从 RTM 生成逐项验证清单 2. 从通用约束生成 P0/P1 规则测试 3. 从时序图异常分支生成异常测试场景 4. 从数据字典生成边界值测试 5. 执行测试并记录结果 6. 对失败项分类根因 |
| 提示词模板 | "请按照 RTM [路径] 逐项验证，参考测试计划 [路径]，报告每项的通过/失败状态和缺陷详情。" |
| 常见坑 | 只测正常路径（边界/异常上线后集中暴露）；RTM 建而不用（规格沦为摆设）；缺陷不分类根因（复盘无法定位系统性问题）；一修 Bug 引入新 Bug（无回归验证）；设计实现不一致但被忽略（"代码能跑就行"心态） |
| 回退影响面 | 发现规格错误 → 回对应阶段（A-D）修正 → 已通过的测试需重跑；发现新缺陷 → 评估是否需要补充测试用例；P0/P1 缺陷 → 必须修复后重新验证 |
| 人确认点 | 测试报告是否覆盖 RTM 全部条目？P0/P1 缺陷是否清零？设计实现一致性是否确认？ |

### 门禁清单

- [ ] RTM 逐项验证通过（无空白、无失败）。
- [ ] 无 P0/P1 缺陷。
- [ ] 设计文档与实现一致（无未记录的偏移）。
- [ ] 异常路径和边界条件已验证。

---

## 8. 阶段 G：发布准备与复盘

| 字段 | 内容 |
|------|------|
| 目标 | 确认部署条件、完成发布、沉淀经验并回填方法论 |
| 产物 | （1）发布清单（部署步骤/回滚方案/验证项）（2）复盘报告（问题根因分析/经验教训/方法论改进建议） |
| 出口条件 | 部署验证通过；回滚方案已准备；复盘报告已输出；经验已区分"项目特定修复"和"方法论改进" |
| 依赖 | 阶段 F 的测试结论和缺陷清单；阶段 E 的变更日志；部署/硬件清单（如有） |
| 规则 | 发布清单必须包含回滚方案（不能只有"怎么上"没有"怎么撤"）；复盘必须按根因分类（来自阶段 F 的缺陷分类）；经验必须区分"项目特定修复"和"可复用方法论改进"——不要把项目专有规则误写成通用规则（见 [09-常见陷阱与最佳实践.md](./09-常见陷阱与最佳实践.md) §9）；软硬件项目必须包含现场验收清单（断网/断电/离线/重启恢复） |
| AI 引导要点 | 1. 从变更日志和缺陷清单总结问题根因分布 2. 判断哪些经验应该回填到模板或方法论 3. 生成发布清单（含回滚方案） 4. 区分"项目特定修复"和"方法论改进"两类建议 5. 如涉及硬件，生成现场验收清单 |
| 提示词模板 | 见 [06-AI协作提示词.md](./06-AI协作提示词.md) §6 |
| 常见坑 | 不写复盘直接结束（同类问题下次重复出现）；把项目特定经验误当通用规则（模板失去通用性）；发布清单没有回滚方案（上线失败无法撤回）；软硬件项目不做现场验收（到现场才发现环境问题） |
| 回退影响面 | 部署验证失败 → 回阶段 E/F 修复 → 重跑发布流程；发现规格层面问题 → 回对应阶段修正 |
| 人确认点 | 发布清单是否完整（含回滚）？复盘改进项是否合理？是否同意发布？ |

## 9. 阶段回退规则

| 发现问题 | 回退到 | 原因 |
|----------|--------|------|
| 需求边界不清 | A | PRD 未定，后续全会漂移 |
| 字段语义冲突 | B | 数据事实源不可靠 |
| 通用规则冲突 | B | 跨模块规则必须先统一 |
| 接口两端不匹配 | C | 无法联调 |
| 架构边界不清 | D | 实现任务无法稳定拆分 |
| 测试无法设计 | A-C | 说明需求、数据、约束或流程不够明确 |
